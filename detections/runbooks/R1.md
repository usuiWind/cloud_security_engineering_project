# R1: activity in an unapproved region

**Rule:** `detections/R1-region.kql`, Sentinel, every 5 min over 1 h. Fires on a *denied* call (`ErrorCode` set) outside us-east-1 and us-west-2, grouped by principal and region. Suppressed for 1 h after it fires.

## What it means
Someone or something tried to act outside the approved regions. The region SCP (`meridian-allowed-regions`) refuses nearly everything there, so the denial is the signal. `sts:*` is exempt from the SCP, so a successful `GetCallerIdentity` in another region is normal alongside a denied call.

## First checks
1. Which principal (`UserIdentityArn`) and which call (`Events`)?
2. Was it the SCP that denied it? `ErrorMessage` says `explicit deny in a service control policy`.
3. Did the same principal succeed at anything in that region (`Calls` minus `Denied`)?
4. Is it you? A lab simulation or a mistyped `--region`.

## Containment
If it isn't you or a known test:
1. Treat the principal's credentials as compromised: disable the SSO user or revoke the session, rotate any access keys.
2. Confirm the SCP is still attached (`aws organizations list-policies-for-target`), since an attacker would try to remove it first.
3. Review that principal's calls in the last 24 h in `AWSCloudTrail`.

## False positives
A new AWS service that calls an unapproved region and is denied. Check the event source before adding a region to the allow list. Never widen the SCP to quiet the alert.
